# Carbon mapping with AlphaEarth covariates

The input folder holds four files for the chosen embedding year. The first three come from Earth Engine. The R script creates the fourth at the requested prediction spacing.

| File | Contents |
|---|---|
| `alphaearth_2024_janousek_cores.csv` | Reference cores, stocks and embeddings |
| `alphaearth_2024_local_cores.csv` | Local core locations, stocks where available and embeddings |
| `alphaearth_2024_aoi.tif` | The 64 embedding bands clipped to the study boundary plus a 100 m buffer |
| `pred_points.csv` | Prediction point IDs and coordinates, blank stocks and embeddings extracted from the AOI raster |

The three point tables share the columns `Core ID`, `Latitude`, `Longitude`, `0-30`, `0-50`, `0-100`, `var1` through `var64`, and `embedding_year`. Coordinates are WGS84 and stocks are kg C/m². Earth Engine marks missing values with `-9999`. R reads those values and empty fields as missing. The R script uses `sf` and `terra` and also accepts `.xlsx` versions of either exported point table using `readxl`. It can read earlier exports with names such as `janousek_embeddings_2024.csv`. Keep one copy of each export. The prediction IDs contain the grid cell number. Keep the AOI GeoJSON used to make the Earth Engine export, as R uses its geometry to clip the prediction grid.

## Prepare and export the inputs

1. Run Script 1 to generate `outputs/script1/mapping_data.csv`. Set `aoi_file` and `planning_cores_file` in [Script 3](../../Script_3_covariate_transfer.R) to the exports from the planning tool. Run `Rscript Script_3_covariate_transfer.R --prepare` from the workshop folder. The script checks the planning coordinates against Script 1, then writes `upload/local_points_upload.csv` with the unique Script 1 IDs and `upload/aoi.zip` with the study boundary. Set `planning_cores_file = NULL` in the settings list to use field coordinates directly if locations changed during sampling. R uses the Script 1 coordinates and stocks for the local Matérn update.
2. In Earth Engine's Assets tab, upload `aoi.zip` as a Shapefile table and `local_points_upload.csv` as a CSV table using `longitude` for X and `latitude` for Y. Use the Janousek table asset already available in Earth Engine, or upload [the prepared Janousek CSV](upload/janousek_core_locations.csv) using the same X and Y columns. Enter all three asset IDs in [the export script](../../helpers/BlueCarbon_AlphaEarth_Export.js). The script can read coordinates from the point geometry when the original coordinate columns are absent. The Janousek settings use stocks in Mg C/ha and convert them to kg C/m². If your asset already uses kg C/m², change the multiplier to 1. The recorded core depth determines which reference stocks are eligible at each depth.
3. Run the export script in the Earth Engine Code Editor. Check the console counts before starting all three tasks. The current upload files contain 12 local cores and 1,284 Janousek cores. Save the two CSVs and the GeoTIFF from Drive in this folder. Keep their original names. If Earth Engine splits the GeoTIFF into tiles, keep all tiles from that export together. The default year is 2024. Change the year in both scripts together. The `rasterBufferM` setting applies only to the GeoTIFF. The export preserves missing coverage, including coastal pixels where the embedding is unavailable.
4. Set `cell_size_m` in the R script to the desired prediction spacing, then run `Rscript Script_3_covariate_transfer.R`. The 250 m default controls the spacing of the prediction grid. Each prediction samples the underlying 10 m raster at its point location. The grid uses the same helper as Script 2 and records the area of each cell inside the AOI.

[Earth Engine table upload guide](https://developers.google.com/earth-engine/guides/table_upload) · [Earth Engine export guide](https://developers.google.com/earth-engine/guides/exporting_images)

The Code Editor map shows the AOI, local and Janousek core locations, and an RGB view of three embedding axes for the export year. Use the Layers menu to switch to the previous year or view the dot product across all 64 axes. Brighter pixels in the similarity layer indicate less similarity, and pixels need valid embeddings in both years to appear.

## How the model works

1. **Find similar reference cores.** At each depth, use Janousek cores with a valid embedding and a stock for that depth. Normalize the embedding vectors to unit length and calculate cosine similarity to each local core or prediction point. The embedding covariance kernel is `exp(-(1 - similarity) / bandwidth)`. Evaluate it between each target and the reference cores and normalize each row to sum to one. The default bandwidth is 0.10. Smaller values give the most similar cores more influence.
2. **Build a prior at each location.** Calculate the weighted mean stock and the weighted sample standard deviation. The standard deviation describes spread among the reference cores. Save the effective number of donors and their highest cosine similarity so the reader can see how much reference support each estimate has.
3. **Update the prior with the local cores.** Fit each depth separately. Convert the two stock moments to a lognormal prior. The covariance between two local locations is the product of their prior log-stock standard deviations and a Matérn correlation based on their distance in metres. Condition that Gaussian process on the logs of positive local stocks, then convert the posterior mean and pointwise standard deviation back to kg C/m². The script reuses the local model's selected Matérn parameters and observation error when the saved run matches the AOI, core data and analysis CRS. Editable defaults apply when that run is absent or `local_model_file = NULL`. The lognormal update needs a positive prior mean and spread and at least one usable local core at that depth.
4. **Export results.** The `outputs/script3_covariate_transfer` folder contains a GeoTIFF for each depth with prior and posterior mean and SD, donor support, a point table of predictions, a local-core prior table and an area summary. The paired `transfer_uncertainty_*cm.tif` files contain the prior and posterior pointwise SD in kg C/m² on the same grid. Masked points remain blank. The area table distinguishes the covered-area total from the full-AOI total. A full-AOI total requires coverage of the entire AOI. Script 4 adds the transfer estimates and SD to the interactive maps and saves a separate transfer summary table.

The bandwidth is a starting value for this analysis. For the later comparison across mapping methods, score predictions on the same outer held-out plots used for the other methods. Select any tuned bandwidth and Matérn parameters using only the training data in each fold.

The AlphaEarth Foundations Satellite Embedding dataset is produced by Google and Google DeepMind. All 64 axes are retained, with `A00` mapped to `var1` and `A63` to `var64`. Using one year for all locations provides a common snapshot of surface conditions.
